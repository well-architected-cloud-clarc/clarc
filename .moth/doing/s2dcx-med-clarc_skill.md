## Decisions

- Goal: a Claude Code skill that turns "draw the architecture of X" into a clarc input JSON, runs `clarc`, and delivers drawio XML. The skill authors only the JSON (nodes, groups, edges, hints) and applies user layout hints; layout, routing, theming and rendering are entirely clarc's job. Nothing is hand-placed.
- Replaces the old c43 `ascii` skill in place (plugin dir `claude-plugin/c43`, skill `skills/ascii`): the cell-grid flow, `layout.py`/`autolayout.py`, their tests and the `uat` fixtures are removed; the plugin/skill are renamed to clarc. This subsumes moth t1yse. Rejected: keeping c43 skill alongside, a second plugin.
- Facts source, two modes, chosen from the request (asked when unclear): (a) discover from code: the agent reads the target project (IaC, docs, specs, existing diagrams) and models what is there; (b) generate from a discussion: the agent interviews the user about a (possibly not yet existing, e.g. phase 3) architecture, plays back the proposed model (nodes, groups, flows) for confirmation, then renders. Modes can be combined (discover, then adjust by discussion). In both, the skill states what to look for (services, network boundaries, data flows vs non-functional links such as DNS/monitoring/identity/config/image pull), never invents components the sources or the user did not give, and asks about unclear spots. Rejected: code-only discovery.
- Input contract is not duplicated in the skill: the skill tells the agent to run `clarc --agentic-help` (per theme: `--aws` default, `--azure`) and follow its example, hint directives, glyph names and edge kinds. The skill only adds workflow guidance. This keeps skill and tool from drifting.
- Interaction model: the skill renders a first version (JSON -> `.drawio` + preview image) with no hints beyond what the sources make obvious (e.g. the `start` node), shows it, and then the USER drives iteration by stating hints in prose ("X on the left", "put Y under Z"). The skill maps each wish onto the `hints` section (`start`, `leftOf`, `rightOf`, `above`, `below`, `sameRow`, `sameCol`), regenerates and shows again, until the user accepts the image. The agent does not self-iterate on aesthetics; it only fixes JSON errors/warnings from stderr (e.g. unknown glyph with suggestions) on its own. Rejected: agent-judged layout tuning loop.
- Preview image: made with the drawio CLI when it is present on PATH (ghost already has it); the skill never installs it. When absent, the skill delivers only the `.drawio` file and tells the user to open it in drawio. Rejected: requiring/installing the drawio CLI, clarc emitting images itself.
- Icon size (clarc rendering): node icons are drawn at twice the earlier size (120 px side instead of 60); label font, edge font and group icons are unchanged. Node squares grow with the icon (grid cells are sized to fit icon + label), so diagrams get larger overall. The reference golden drawio files were regenerated accordingly. Rejected: leaving size as is (icons read too small next to the labels), a user-facing size option.
- Node label size: the label under a node icon is set at 16 px (was 12) to match the bigger icons, and node squares are sized so the wrapped label still fits. Notes, group titles and edge labels keep their size. Rejected: scaling every text, a user-facing font option.
- Edge ends on a node's bottom: an edge leaving or entering a node from below attaches just under the label text (a small gap below it), not at the bottom of the node's square, which has slack below the label; otherwise non-functional flows (which run top to bottom) appear to start far from their node. Covered by a unit test on the port offset.
- Even port spacing wins over straight lines: ports on a node side are evenly spread, except that the layout engine may move a port to the height of its facing port so a same-row connection runs straight, and only when the moved port is alone on its side. A side with several ports is never disturbed (it made inbound connectors on buckets unevenly spaced). Engine change (c43-layout repo, tagged with this task); a few connections that used to be straight now take a small jog. Rejected: never snapping (loses clean single-port straight lines), snapping when either side is busy, compensating in clarc only.
- Output: JSON and resulting `.drawio` are saved in the project (next to the docs of the thing being drawn), named per diagram; JSON is kept so the diagram can be regenerated and tweaked later.
- Binary acquisition: order of preference is `clarc` on PATH, then the user-level cached copy (`~/.local/share/clarc/clarc`), then download of the matching archive from the rolling `latest` GitHub release of the clarc repo (assets `clarc-<sha>-<target>`, with `SHA256SUMS`; verify checksum) into that cache. OS/arch picks the target. A cached copy is never refreshed automatically (delete it to re-download); while developing, the freshly built binary is copied over the cache after each rebuild so other sessions use it. Rejected: requiring a manual install only, building from source.
- First test case: `~/projects/ghost` (repo "ghosted"). Phase 2 is reproduced from `phase2/iac` as the check of the skill, then the same flow renders phase 3 (`phase3/`: serverless Ghost behind CloudFront with Lambda function URLs, content and SQLite-store buckets, EventBridge schedules, CloudWatch, SSM, SMTP provider) from code plus discussion. Phase 3 facts come from the user/docs, never from the skill. Acceptance: the user iterates hints on the rendered image until satisfied; rendering defects found on the way (icon/label size, edge ends, port spacing) are fixed in clarc and the engine, not worked around in the JSON.

- Demo and documentation: the repo README presents the tool (usage, input model, install from the rolling release or cargo) and the skill (workflow, how to enable it in a session) and embeds an animated demo of building the phase 3 diagram by conversation (plus a video version). The demo is a mock Claude Code session on the left (user requests typed on a dark-grey bar, skill/clarc calls, trimmed replies) and the diagram on the right, updating after each reply; about 30 s, 1400 px wide, followed by a 10 s hold on the finished diagram; steps that changed nothing are left out. It is generated from a recorded step list (request, reply, graph per step) by a script kept with it, so it can be regenerated when rendering changes. Rejected: screen-recorded terminal, full-length replies.

## Phase 2 reference model (read from ghost `phase2/iac/*.tf`; expected content of the first test diagram)

- Edge: viewer -> CloudFront (alias of the site domain, DNS zone points at it, ACM cert). Path behaviours: default -> existing marketing S3 bucket (OAC); `blog*` and `blog/ghost*`, `blog/members*` -> Lightsail container service (custom https origin); `blog/content/images*` -> origin group (data S3 bucket via OAC, failing over to the container on 403).
- Compute: Lightsail container service (Ghost + sqlite-s3 launcher, single node), image pulled from ECR through the service's private-registry puller role (nf link).
- Container reaches AWS only via AssumeRole into an IAM role in our account; role grants: data bucket CRUD (SQLite segments/manifest/leases + images), SSM Parameter Store read + KMS decrypt (mail credential), CloudWatch PutMetricData. Container also talks SMTP to an external mail provider.
- Observability (nf): CloudWatch alarms on boot metrics -> SNS topic -> email subscription; CloudFront access logs delivered to a CloudWatch log group.
- Flags in the IaC (`deploy_lightsail`, `deploy_cloudfront`) toggle parts of this; the diagram shows the fully deployed state. Secrets/ARNs/account ids never go into the JSON or diagram.

## Implementation (abstract)

- Plugin manifest and marketplace entry renamed to clarc; single skill whose SKILL.md carries: trigger description, the workflow (inspect project -> `clarc --agentic-help` -> write JSON -> run clarc -> review -> adjust hints), modelling guidance (node vs group vs data/nf edge), and the binary bootstrap procedure.
- Any bootstrap helper is a small script shipped with the skill; no layout code remains in the plugin.
- Bootstrap helper: PATH, cache, release download in that order (see decisions); prints the path of the usable binary.
- Rendering fixes made on the way live in clarc (icon and label sizes, edge ends under labels) and in the layout engine repo (port snapping rule); the engine repo is pinned by git rev in clarc and the pin is bumped to the commit carrying the change.
- The demo is built by rendering every recorded step with clarc and drawio, then composing frames (mock terminal + diagram) and encoding GIF and MP4; it lives in a `demo/` folder in the repo.
- Validation of the skill is by running it against the ghost repo, not unit tests; repo `cargo build --release` and `cargo test` must stay green (the clarc goldens are regenerated whenever rendering or engine behaviour changes).
